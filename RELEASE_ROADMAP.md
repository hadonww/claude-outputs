## 1. Где мы сейчас (коротко)

Учебное ядро — сильное и проверенное: детерминированный планировщик, SRS, долг, слабые слова, 42 сценарных урока HSK 1, серверная проверка ответов, итог урока. Интерфейс отполирован и проверен.

Иначе говоря: «тренер» готов на ~70%, «продукт для чужих людей» — на ~25%.

### 2.7 Инварианты Phase I.1, которые нельзя нарушить
1. Сценарный урок получает **ту же** норму новых слов, что и обычный (`mix.new_word_budget`), и не превышает её.
2. Долг (> 12) и низкая точность важнее хвоста модуля (`MODULE_TAIL` не добирается).
3. Незнакомые слова — **только** как неверные варианты ответа (`test_unknown_word_rule.py`, 689 таких вариантов за HSK 1 — допустимо).
4. Каждое слово HSK 1 — новое ровно в одном уроке; любая правка `data/lessons` → `validate_hsk1_course.py`.
5. Повторов после ошибок ≤ `MAX_RETRIES_PER_LESSON` (3); review в уроке ≤ 4 (при долге ≤ 6).
6. Слабые идут первыми, в том числе слабые из других модулей.
7. Забытое слово остаётся «знакомым» для фраз (`_base_known`).
8. Правильность решает сервер; LLM нет нигде в коде (проверено grep).
9. Цвета только из токенов; паритет Light/Dark и контраст — тестом.

## 7. PHASE 5 — реальные учебные функции

### Произношение
Путь: `MediaRecorder` → `POST /api/sessions/{id}/steps/{i}/speech` → `assess_pronunciation` → `engine.pronunciation.score_utterance` (0–100, порог 60) → `Attempt` навыка `speaking`. Не хватает только провайдера.

| Вопрос | Ответ |
|---|---|
| API | кандидаты: Azure Speech Pronunciation Assessment (zh-CN), Tencent SOE, iFlytek ISE. Цены, хранение аудио и доступность оплаты из РФ нужно проверить перед выбором — **решение владельца** |
| Где хранится результат | `attempts` (skill `speaking`), `state.speech` сессии; аудио не хранится — так и оставить |
| Ошибка API | `PronunciationUnavailable` → `{available:false}`; шаг не засчитывается |
| Fallback | «Послушай и повтори» без оценки (B3: сейчас сначала записывает) |
| Latency | синхронный вызов в запросе; нужен таймаут ~5 с |
| Privacy | голос уходит третьей стороне → отдельное согласие + строка в Privacy Policy |
| Несоответствие контракта | `recognize()` возвращает «услышанный пиньинь», а Azure/SOE отдают баллы по слогам — адаптер придётся писать под баллы (M) |

**Вывод:** без оценки произношения можно нормально учиться каждый день → **не блокирует beta**. Блокирует beta только B3. Провайдер — P2.

### Аудио
0 файлов, только `speechSynthesis`. Повторное воспроизведение и одновременный звук обработаны. Но качество и само наличие звука зависят от ОС пользователя, а аудирование — ~15% шагов HSK 1. **MUST:** заранее сгенерировать mp3 нейросетевым TTS для 165 слов HSK 1, всех фраз сценариев, примеров и диалогов (~500–700 файлов), положить в `audio/`, научить фразы играть по id (сейчас по id играют только слова). TTS остаётся fallback.

### Письмо
HanziWriter, ввод работает, допускается 2 ошибки, есть отметка завершения. Ограничения: только первый иероглиф; 40 иероглифов HSK 1 грузятся с CDN `@latest`. Нужно: завендорить все иероглифы HSK 1–2 и зафиксировать версию (S), проверить лицензию данных (Arphic PL / LGPL — указать в About).

## 14. Утверждённые решения (v3)

### 14.1 Auth — минимальный собственный multi-user, без привязки к Telegram
- **Учётная запись**: `users` (как сейчас: внутренний `id`, публичный `public_id`) + новая таблица
  `user_identities(user_id, provider, subject, secret_hash, created_at)`. Первый провайдер —
  `password` (email или логин + пароль). Telegram / Apple / Google позже — новые строки в этой
  таблице и новый эндпоинт входа; **learning engine, сервисы и учебные таблицы не меняются**.
- **Пароли**: только хеш — `hashlib.scrypt` из стандартной библиотеки (без новой зависимости) с
  солью на пользователя и параметрами в строке хеша (можно сменить алгоритм без миграции).
  Минимальная длина 8, сравнение за постоянное время.
- **Сессии**: случайный токен 32 байта в cookie `HttpOnly; Secure; SameSite=Lax`; в БД
  (`auth_sessions`) — только хеш токена, срок жизни, `last_seen`; выход и «выйти везде» удаляют строки.
- **CSRF**: SameSite=Lax + изменяющие запросы только с `Content-Type: application/json` (форма
  чужого сайта такой не пошлёт).
- **«Кто делает запрос»**: FastAPI-зависимость `current_user` в роутерах вместо
  `users_repo.get_current_user_id`; сервисы и репозитории получают `user_id` параметром.
- **Регистрация в beta**: по инвайт-коду (контроль числа тестировщиков, защита от ботов).
  Сброс пароля в beta — админ-скриптом; сброс по email — P1 (нужен почтовый сервис).
- **Rate limit входа**: по IP и по логину (базовая безопасность, P0).
- **Миграция**: существующий единственный пользователь становится владельцем своего прогресса
  (`user_id = 1`), ничего не теряется.

### 14.2 Hosting и 152-ФЗ — переносимая архитектура, юридическая проверка отдельным этапом
- Ничего провайдер-специфичного: один процесс приложения + SQLite (WAL) на томе + reverse proxy
  с автоматическим HTTPS (Caddy) + бэкап в любое S3-совместимое хранилище (Litestream или
  ночной `.backup`). Вся конфигурация — переменные окружения (`.env.example` в репозитории,
  секреты — нет).
- Упаковка: Dockerfile + `compose` (приложение + Caddy) **и** описание запуска через systemd —
  переезд = скопировать том/бэкап и поднять на новом сервере. Проверка переносимости: восстановить
  продакшен из бэкапа на чистой машине (входит в T18).
- Выбор страны/провайдера не блокирует разработку; для beta — любой VPS.
- **T51 Legal review персональных данных** (152-ФЗ, локализация, состав данных, Privacy/Terms,
  трансграничная передача для TTS/Sentry) — **обязательный этап перед public (P1)**. Возможный
  итог — переезд на другой хостинг, поэтому переносимость обязательна.

### 14.3 Audio — только заранее подготовленные файлы
- Browser TTS **не считается production audio**: в продакшене он не используется как замена.
- Конвейер `scripts/build_audio.py --level N`: манифест «текст → хеш → файл», идемпотентно
  (повторный запуск догенерирует только недостающее/изменённое), файлы в `audio/words/`,
  `audio/sentences/`, отчёт покрытия по уровню. Сервис TTS — за адаптером (как провайдер речи).
- Фразы, примеры и реплики диалогов играются **по своему id/хешу**, а не только слова.
- Упражнение, которому нужен звук (listening, sentence_listening, tone_choice на слух…),
  в реестре получает `requires: есть аудио` — планировщик **не ставит** его без файла. Кнопка
  звука без файла не показывается. Так отсутствующее аудио делает урок беднее, но не ломает его.
- Порядок генерации: **HSK 1 → HSK 2 → HSK 3 → HSK 4**, отдельной веткой; backend её не ждёт.
- Проверка: автоматически (файл есть, длительность в разумных пределах, не пустой) + выборочное
  прослушивание ревьюером (полиметрия: 了, 得, 行, 长… — 100% слов с несколькими чтениями).

### 14.4 Проверка контента — правило остановки с исключением для критических ошибок
**Критическая ошибка** (исправляется всегда, независимо от процента): неверное значение слова,
неверный пиньинь или тон, неверный иероглиф, пример/диалог с грамматической ошибкой или
искажённым смыслом, ключ ответа, который принимает неверное или отвергает верное, аудио с неверным
чтением, оскорбительный или неуместный текст.
**Некритическая**: стилистика перевода, неполнота значения, неестественная, но верная фраза.

Процесс для каждого уровня:
1. Первые 2 модуля уровня — **100%** проверки.
2. Остальные — **минимум 10%** случайной выборки (слово + перевод + пиньинь + пример + аудио).
3. Выборка чистая (некритических ≤ 5%) и **нет критических** → уровень можно выпускать.
4. Много ошибок (> 5%) **или систематическая проблема** (одна и та же причина ≥ 3 раз:
   многочтение, перевод одной части речи, шаблон примеров) → расширить проверку на весь
   затронутый класс (модуль, часть речи, все многочтения, весь уровень).
5. После расширенного прохода — **новая** случайная выборка 10% и повторная оценка по п. 3.
6. Каждая найденная критическая ошибка → проверить, нет ли той же причины в остальных словах
   уровня (поиск по шаблону), и добавить автоматическую проверку, если её можно формализовать.

| | HSK 1 | HSK 2 | HSK 3 | HSK 4 |
|---|---|---|---|---|
| Ручная проверка | 100%, до beta (P0) | 100%, до public (P1) | правило выше, до public (P1) | правило выше, до public (P1) |
| Автопроверка: 0 unknown words, структура, примеры, упражнения | ✅ есть (P0) | T44 (P0) | T44 (P0) | T44 (P0) |
| Аудио | P0 | P0 | P0 | P0 |
| Сценарные уроки | 42 (есть) | не нужны | не нужны | не нужны |

### 14.5 Бюджет новых слов — HARD MAX по уровню
- Единица бюджета: слово с новым для ученика иероглифом = **1**; слово, все иероглифы которого
  ученику уже знакомы (из слов с попытками или отмеченных placement), = **0,5**.
- **HARD MAX**: HSK 1 = **5**, HSK 2 = **6**, HSK 3 = **7**, HSK 4 = **8** единиц. Это потолок,
  а не целевой объём: обычный урок берёт норму от минут онбординга и точности, потолок только
  срезает лишнее.
- Порядок правил сохраняется: **accuracy → debt → module tail → level cap**. Хвост модуля
  добирается только в пределах потолка.
- Инварианты Phase I.1 не меняются: сценарий не получает больше нормы обычного урока; долг и
  низкая точность важнее хвоста; повторов после ошибок ≤ 3; слабые первыми.
- Убрать второй порог «малого долга» (`REVIEW_CAP = 8` в бонусе точности) → `BACKLOG_THRESHOLD`.
- Тесты: 4 ученика × 4 уровня — «новое ≤ HARD MAX уровня», «медиана 18–26 шагов», «долг убывает»;
  unit-тест таблицей (уровень, норма, точность, долг, хвост → число слов).

### 14.6 Placement — короткий адаптивный, без ложного mastery
- **Формат**: 12–20 заданий, ≤ 4 минут. Лестница по уровням: старт с уровня, который назвал
  пользователь в онбординге; 4–5 заданий уровня (значение по иероглифу, слово на слух, иероглиф по
  значению), слова — частотные из разных модулей уровня; ≥ 80% → уровень выше, < 60% → ниже,
  между — 2 дополнительных задания. Выбор заданий детерминирован (seed = пользователь), только
  по уже данным ответам (правило lookahead из AGENTS.md).
- **Результат**: стартовая точка HSK 1 / 2 / 3 / 4 (первый модуль уровня). Вариант «я новичок» —
  сразу HSK 1 без теста.
- **Критично — без массового ложного mastery**: слова нижних уровней получают отдельную отметку
  **«известно по placement»** — не `mastered`, не в SRS, без due-даты. Для движка они «знакомы»
  (фразы, дистракторы, знакомые иероглифы бюджета), но в статистике и словаре не считаются
  выученными. Их постепенно проверяет существующий механизм retention (≤ 1 слово за урок);
  ошибка → слово уходит в обычное обучение. Попытки пишутся только по реально показанным заданиям.
- **Доступ**: модули уровней ниже стартового — открыты (серверная запись разблокировки), выше — по
  маршруту. Пройти placement повторно — из настроек (P1).
- **Отдельные тесты (P0)**:
  - placement → HSK 1 (новичок / все ответы неверны): 0 отметок, первый урок = «Привет! Меня зовут…»;
  - placement → HSK 2, → HSK 3, → HSK 4 (профили ответов): верный стартовый модуль;
  - **нет ложного mastery**: после placement `mastered = 0`, due-слов = 0, в SRS только показанные слова;
  - **корректный стартовый урок**: первый урок уровня строится, 0 unknown words, новых ≤ HARD MAX;
  - закрытый модуль выше стартового → 403 от сервера;
  - retention: placement-слово с ошибкой переходит в обучение, не ломая долг.

### Первый coding task: **T11 — multi-user модель данных** (после T01)
Почему он: от него зависят auth, изоляция, placement, resume и бюджет — весь критический путь.
Делается **без экрана входа**: пока остаётся один пользователь по умолчанию, но каждая учебная
таблица и каждый запрос уже работают «по пользователю».

Объём:
- `progress` → ключ `(user_id, word_id)`; `stats` → строка на пользователя; `activity_log` →
  `(user_id, day)`; настройки — на пользователя; проверить `attempts`, `mastery`,
  `mastery_history`, `review_schedule`, `lesson_sessions`, `lesson_completions`, `entitlements`.
- Миграция существующей БД: все строки → `user_id = 1`, данные не теряются; новая и старая БД
  дают одинаковые ответы API для пользователя 1.
- Репозитории и сервисы получают `user_id` параметром; `get_current_user_id` вызывается только в
  роутерах (одна точка замены для T10).
- Новый пользователь получает свой пустой прогресс (`progress` строится лениво или при создании).
- Тесты: два пользователя на сервисном уровне — ответы A не меняют прогресс, статистику, серию,
  due-слова, сессии B; миграция копии старой БД; весь существующий набор (483) зелёный;
  `validate_hsk1_course.py` и `simulate_users.py` без изменений результата.
- Документы: `ARCHITECTURE.md` (таблицы, инвариант 12), `CURRENT_STATE.md`.
- Код engine не меняется.

Оценка: L (3–5 дней). Один этап — один коммит, отчёт и остановка.
